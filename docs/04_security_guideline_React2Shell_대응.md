## 1. 문서 개요

### 1.1 목적

이 문서는 최근 공개된 React Server Components(RSC) 취약점(일명 React2Shell) 이슈를 계기로,  
**MES-System_v_0.5** 프로젝트의 보안 구조를 점검하고, 앞으로 개발·운영 단계에서 따라야 할  
**실질적인 보안 가이드라인**을 정리하기 위한 문서이다.

특히 다음 내용을 목표로 한다.

- React2Shell 취약점이 무엇인지 쉽게 이해할 수 있도록 설명
- MES-System_v_0.5의 기술 스택과 비교하여 **직접적인 영향 여부**를 평가
- 간접적으로 배워야 할 보안 교훈과 **설계 원칙**을 정리
- 데이터 암호화, 멀티테넌트, 라이브러리 관리, 운영 보안 측면의 **구체적인 실천 항목** 제시

### 1.2 적용 범위

- 대상 시스템  
  - GitHub: `MES-System_v_0.5` 저장소
  - 백엔드: NestJS + TypeORM + MariaDB
  - 프론트엔드: React + Vite + TypeScript + Ant Design (+ Recharts)
- 이 문서는 2025-12 기준 설계와 구현 상태를 반영하며,  
  이후 기능 확장 시에도 기본 보안 원칙으로 유지한다.

## 2. React2Shell 취약점 요약

### 2.1 React Server Components(RSC)란 무엇인가

- React 18 이후 도입된 기능
- **브라우저(클라이언트)가 아닌 서버에서 React 컴포넌트를 렌더링**하고,
- 그 결과를 **Flight 프로토콜**이라는 특수한 포맷으로 브라우저에 전달하는 구조
- Next.js 13+ App Router, 일부 프레임워크에서 RSC를 활용

핵심 개념은 다음과 같다.

- 클라이언트 → 서버로 “어떤 컴포넌트를 어떻게 렌더링할지” 요청
- 서버 → React 컴포넌트를 실행하고 결과를 Flight 데이터로 응답
- 클라이언트 → 이 Flight 데이터를 해석해서 화면을 업데이트

이 과정에서 **서버와 클라이언트 사이에 복잡한 직렬화/역직렬화 로직**이 존재한다.

### 2.2 React2Shell(CVE 계열) 개요

React2Shell은 위 RSC 기능의 설계 취약점을 이용해,  
**비인증 상태에서 서버 측에서 임의 코드 실행(RCE)을 할 수 있게 만드는 공격 기법**이다.

주요 특징:

- 공격자는 RSC 엔드포인트(Flight 엔드포인트)에 **악의적인 Flight 페이로드**를 보내,
- 서버 쪽 RSC 처리 로직이 이 데이터를 **검증 없이 객체로 복원**하도록 유도하고,
- 특정 조건에서 서버 내부의 민감 객체(예: 함수, 모듈)에 접근해
- 최종적으로 `child_process.exec` 등으로 **OS 명령 실행**까지 이어질 수 있다.

특징 요약:

- **비인증 RCE 가능**
- **Zero-click 공격 가능** (사용자 행동 없이 서버에 직접 요청)
- 이미 **PoC와 자동 스캐너가 공개**되어 전 세계 RSC/Next.js 서버가 실제로 스캔되고 있음
- 패치되지 않은 RSC/Next.js 서버는 Log4Shell 급의 위험도로 평가됨

### 2.3 취약점이 성립하는 기술 조건

React2Shell 공격이 성립하려면 보통 다음 중 하나 이상이 필요하다.

1. 서버에서 React Server Components(RSC)를 사용
2. Next.js 15/16 App Router 기반으로 RSC/Server Actions 사용
3. RSC를 지원하는 SSR 프레임워크를 서버에서 사용

즉, **“React를 서버에서 렌더링하는 구조”**가 있어야 하고,  
단순 클라이언트 렌더링(CSR)만 사용하는 React 앱은 이 취약점의 직접 공격 대상이 아니다.

## 3. MES-System_v_0.5 아키텍처와 React2Shell 영향 분석

### 3.1 현재 아키텍처 요약

1) 프론트엔드(client)

- React 19.x + React DOM 19.x
- Vite + @vitejs/plugin-react
- 브라우저에서만 렌더링하는 **순수 클라이언트 렌더링(CSR) SPA 구조**
- Next.js, RSC, React Server DOM 관련 패키지를 사용하지 않음

2) 백엔드(server)

- NestJS 기반 REST API 서버
- TypeORM + MariaDB
- JWT 기반 인증, bcrypt 기반 비밀번호 해시
- AES-256-GCM 기반 데이터 컬럼 암호화(EncryptedTransformer) 적용
- React, Next, RSC 관련 패키지를 사용하지 않음

3) 공통

- client/server는 완전히 분리된 구조
- 서버는 React 렌더링을 하지 않고, 오직 JSON 기반 API만 제공

### 3.2 직접적인 RCE 위험도 평가

위 구조를 기준으로 하면:

- 서버는 **React Server Components를 전혀 사용하지 않음**
- Next.js 기반이 아니고, RSC/Server Actions 엔드포인트도 없음
- React는 브라우저에서만 실행되며, 서버는 NestJS API만 담당

따라서 **React2Shell 취약점이 직접적으로 적용될 수 있는 기술 조건 자체가 없다.**

결론:

> 현재 MES-System_v_0.5 구조에서는  
> React2Shell 취약점으로 인한 직접적인 원격 코드 실행(RCE) 위험도는  
> **사실상 0에 가까운 수준**이다.

## 4. React2Shell 이슈로부터 얻는 보안 교훈

직접적인 영향은 없지만, 이번 이슈가 주는 교훈은 크다.  
우리 시스템에 바로 적용할 수 있는 교훈들을 정리하면 다음과 같다.

### 4.1 “클라이언트 입력”과 “서버 코드 실행” 사이의 거리 유지

- RSC/Server Actions는 클라이언트 요청이 **거의 곧바로 서버 함수 실행**으로 이어지는 구조였다.
- 이런 구조는 개발자는 편하지만, **중간 검증/필터링 계층이 부족**해지기 쉽다.
- MES-System에서는 다음 원칙을 지킨다.

원칙:

1. **서버에서 동적 코드 실행 금지**
   - `eval`, `new Function`, `vm.runInNewContext` 등 사용 금지
2. **OS 명령 실행 최소화**
   - `child_process.exec`, `spawn` 등은 가능한 사용하지 않는다.
   - 필요한 경우에도 **고정된 스크립트 + 제한된 인자**만 허용하고,
   - 사용자 입력을 곧바로 명령 문자열에 합치지 않는다.
3. **DTO + class-validator 강제 사용**
   - 모든 API 입력은 DTO 클래스로 정의하고,
   - class-validator로 타입·길이·패턴 등을 검증한 뒤 서비스 로직으로 전달

### 4.2 프레임워크 자동 기능의 “편리함” 뒤에 있는 위험 인식

- 자동 직렬화, 자동 RPC, 자동 바인딩 기능은 생산성을 높이지만,
- 내부 구조를 잘 이해하지 못한 상태에서 사용하면 **대형 취약점**으로 이어질 수 있다.

MES-System에서는:

- 현재처럼 NestJS + DTO + Service 계층 구조를 유지하고,
- 이후 다른 프레임워크(예: Next.js, RSC 기반 SSR)를 도입할 때는  
  반드시 **보안 관점 설계 검토**를 선행한다.

### 4.3 신규 기술 도입 시 “보안 패치 상태” 우선 확인

- 향후 성능·SEO 이유로 SSR/Next.js 도입을 검토할 수 있다.
- 이때는 다음을 반드시 확인한다.

1. 도입하려는 프레임워크 버전이  
   - 이미 React2Shell 및 관련 CVE들이 **패치된 버전인지**
2. RSC/Server Actions를 실제로 사용할 필요가 있는지
   - 사용하지 않는다면 기본으로 비활성화
3. 사용하는 경우
   - RSC 엔드포인트, Server Action 경로를 문서화하고
   - WAF/로깅/모니터링 설정에 반영

## 5. 데이터 암호화 가이드

### 5.1 현재 구현 상태 요약

- 비밀번호
  - bcrypt 해시로만 저장 (복호화 불가)
- 일반 개인정보 및 민감 정보
  - User 엔티티의 일부 필드(이름, 전화번호, 회사명 등)에  
    AES-256-GCM 기반 EncryptedTransformer 적용
  - LoginHistory 엔티티의 IP, User-Agent 등도 암호화 저장
- 암호화 키
  - `.env` 파일의 `DATA_ENCRYPTION_KEY_BASE64` 환경 변수에서 32바이트 키를 Base64로 읽어 사용
  - 키 길이가 잘못되면 서버 구동 시 즉시 에러를 발생시켜 정상 기동을 막음

### 5.2 암호화 적용 원칙

1. **비밀번호는 항상 해시(bcrypt/argon2 등)**
   - 평문이나 복호화 가능한 형태로 저장 금지
2. **민감 컬럼은 AES-256-GCM 암호화**
   - 개인 정보: 이름, 이메일, 전화번호, 주소, 주민등록번호, 계좌번호 등
   - 로그 중 민감한 정보: IP, User-Agent, 에러 메시지에 포함된 민감 값 등
   - 경영 데이터: 거래처명, 담당자 연락처, 중요한 계약 조건 등
3. **검색이 필요한 컬럼은 별도 설계**
   - 예: 회원 검색을 위해 이름/이메일로 검색이 필요할 경우
   - 암호화된 값만으로는 index 검색이 어려우므로,
     - 검색 키로 사용할 값에 대한 해시 컬럼을 추가하거나
     - 검색 조건을 제한하는 방향으로 설계

### 5.3 키 관리 및 운영 원칙

1. **코드에 키 하드코딩 금지**
   - 암호화 키는 `.env` / 운영환경 시크릿 스토어에만 존재
2. **키 교체(회전) 정책**
   - 운영 단계에서 주기적으로 키를 교체할 수 있는 구조 검토
   - 예:
     - `KEY_V1`, `KEY_V2` 같이 버전별 키를 두고
     - 새로 저장되는 데이터부터 새 키를 사용
     - 백그라운드 배치로 구 데이터 재암호화
3. **로그에 민감 값 기록 금지**
   - 암호화/복호화 실패 시에도 평문 데이터를 로그에 남기지 않는다.
   - 에러 메시지는 “복호화 실패” 등 일반적인 문구로 제한

### 5.4 신규 엔티티 정의 시 체크리스트

신규 테이블·엔티티를 만들 때마다 아래 항목을 검토한다.

- [ ] 이 엔티티에 **개인 정보**가 포함되는가?
- [ ] 이 엔티티에 **민감한 업무 정보(단가, 계약 조건, 내부 코드 등)** 가 포함되는가?
- [ ] 포함된다면 해당 컬럼에 **EncryptedTransformer** 를 적용했는가?
- [ ] 검색/정렬이 필요한 컬럼에 대해 별도 설계를 했는가?
- [ ] DTO/검증 로직에 값의 포맷·길이·범위를 명확히 정의했는가?

## 6. 멀티테넌트(기업별) 보안 가이드

### 6.1 기본 개념 정리

MES-System은 **다수의 기업**이 하나의 시스템에 접속해  
각자 자신의 제조 데이터를 관리하는 **멀티테넌트 구조**를 목표로 한다.

핵심 개념:

- `Company` = 하나의 기업(고객)
- `User` = 반드시 한 Company에 속함
- `LoginHistory` 등 모든 이력은 Company와 연결
- 관리자:
  - SYSTEM_ADMIN: 모든 회사 관리
  - COMPANY_ADMIN: 자신의 회사만 관리
  - USER: 일반 사용자

### 6.2 설계 원칙

1. **모든 도메인 데이터는 Company 단위로 분리**
   - 수주, 품목, 재고, 생산, 설비, 품질 등 모든 엔티티에  
     `companyId` (혹은 Company 관계)를 포함
2. **모든 쿼리는 Company를 필수 조건으로 사용**
   - 서비스/리포지터리 계층에서
     - 항상 `(companyId, 기타 조건)` 방식으로 조회
   - SYSTEM_ADMIN만 회사 필터를 바꿀 수 있고,
     일반 사용자는 자신의 회사만 조회 가능
3. **관리자용 “기업 선택 필터” 공통 제공**
   - 시스템/서비스 관리자는 화면 상단에서 회사 선택
   - 선택된 회사 정보는
     - 프론트 전역 상태에 저장
     - API 요청 헤더(ex. `X-Company-Id`)에 포함
   - 백엔드는
     - JWT의 role, companyId, `X-Company-Id` 를 함께 검증해 권한을 판정

### 6.3 멀티테넌트 보안 체크리스트

- [ ] User, Company, LoginHistory 관계가 올바르게 설정되어 있는가?
- [ ] 각 API에서 현재 회사 컨텍스트를 올바르게 파악하는가?
  - SYSTEM_ADMIN → 헤더/쿼리의 회사 선택값 사용
  - COMPANY_ADMIN/USER → JWT의 companyId만 사용
- [ ] 조회/수정/삭제 쿼리에서 다른 회사 데이터가 섞여 나올 가능성이 없는가?
- [ ] 관리자 화면에서 “기업 선택” UI가 제대로 동작하는가?

## 7. 라이브러리·취약점 관리 가이드

### 7.1 React2Shell 관련 버전 정책

- 현재 프론트는 React 19.x를 사용하나,  
  RSC는 사용하지 않으므로 React2Shell의 직접 영향은 없다.
- 그럼에도 다음 정책을 따른다.

1. React/React DOM은 **보안 패치가 포함된 버전 이상**으로 유지
2. RSC/SSR 도입 시에는
   - 해당 시점의 React/Next 보안 공지와 권장 버전을 반드시 확인
   - 최소 요구 패치 버전 이상으로만 배포

### 7.2 GitHub 보안 기능 활용

- GitHub 리포지터리에서 다음 기능을 활성화한다.
  - Dependabot 보안 알림(Dependency graph > Dependabot alerts)
  - Dependabot 버전 업데이트(PR 자동 생성)
- 취약점 알림이 오면:
  - 영향 범위를 검토
  - dev 브랜치에서 버전 업그레이드 후 빌드/테스트
  - 문제 없으면 main에 병합

### 7.3 npm audit / SCA 도입

- client/server 각각에 대해 정기적으로 다음을 수행한다.
  - `npm audit` 또는 `pnpm audit`
- 장기적으로는 SCA(Software Composition Analysis) 도구 도입 검토
  - 예: Snyk, Trivy, GitHub Advanced Security 등

## 8. 운영·배포 보안 가이드 (요약)

### 8.1 OS/런타임 보안

- Linux/Windows 공통:
  - 애플리케이션은 **비루트 계정**으로 실행
  - OS 및 패키지를 주기적으로 업데이트
- Node.js:
  - **LTS 버전** 기준으로 통일 (예: Node 20 LTS)
  - EOL이 지난 버전 사용 금지

### 8.2 네트워크·WAF 설정

- 외부에 노출되는 포트 최소화 (예: 80/443 + 필요한 DB 포트 내부망 제한)
- 리버스 프록시(Nginx/Apache) 앞단에서:
  - 요청 크기 제한
  - 비정상적인 경로/메서드 차단
  - API 경로와 정적 리소스 경로를 명확히 구분
- WAF 사용 시:
  - REST API에 대한 기본 공격 패턴(SQLi, XSS, RCE 시그니처 등) 필터 적용
  - 향후 SSR/RSC 도입 시 RSC 엔드포인트를 별도 모니터링

## 11. 추가 보완 권고(현행 프로젝트 반영)

1) JWT 만료/로그아웃
- JWT 기본 만료 1시간(운영 시 30분~1시간 권장). 만료 시 자동 로그아웃·재로그인 유도.
- 토큰 저장소(localStorage)는 사용하지만, 401/403 응답 시 즉시 삭제하고 메인으로 리다이렉트.

2) 계정 잠금/해제 절차
- 로그인 실패 5회 이상 → isLocked=true, 관리자만 해제.
- 잠금 해제 시 failedLoginCount=0 초기화(현재 서버 로직 반영). UI에서도 관리자만 해제/상태 변경 가능하도록 제한.

3) .env 및 키/비밀번호 관리
- `.env*`는 Git에서 제외(.gitignore 유지), 운영에서는 환경변수/시크릿 매니저 사용.
- `DATA_ENCRYPTION_KEY_BASE64` 32바이트(Base64) 유지, 유출 시 즉시 회전.
- DB 계정/패스워드도 코드/이미지에 포함 금지, 운영용은 별도 계정/권한 최소화.

4) 멀티테넌트 필터 재확인
- SYSTEM_ADMIN만 X-Company-Code 헤더 허용, COMPANY_ADMIN/USER는 JWT companyId만 사용.
- 모든 조회/수정/삭제 쿼리에 companyId 필터가 적용되었는지 점검(도메인 확장 시에도 반복 확인).

5) 정기 점검
- `npm audit`/Dependabot 알림 대응, LTS Node/라이브러리로 유지.
- 신규 엔티티 추가 시 암호화/검색 설계 체크리스트(5.4)를 반복 적용.
