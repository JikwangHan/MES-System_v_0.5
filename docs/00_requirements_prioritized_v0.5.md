문서 버전: v0.5

파일명: `00_requirements_prioritized_v0.5.md`  
적용 대상: MES-System_v0.5 (멀티테넌트, 암호화, 백업 및 복구, 원시 로그 보관, 단일 설치 배포 포함)  
작성 목적: 요구사항을 우선순위로 정렬하고, 재사용성과 단순성 중심의 코딩 표준으로 품질 및 운영 리스크를 사전 차단

## 1. 문서 개요

이 문서는 MES-System_v0.5 프로젝트의 전체 요구사항을 우선순위(P0, P1, P2, P3) 기준으로 정리한 문서이다.  
우선순위는 아래 기준을 종합적으로 고려하여 결정한다.

- 신속성: 실제 개발 적용의 시급성
- 중요성: 시스템 목적 달성에 미치는 영향
- 보안성: 보안 사고 및 데이터 유출 방지와의 직접적 연관성
- 기밀성: 개인정보 및 민감 데이터 보호와의 연관성
- 시스템 관리 용이성: 운영, 유지보수, 배포, 장애 대응의 편의성
- 기능 확대 용이성: 향후 기능 추가 및 확장 시 구조적 유연성

### 1.1 적용 범위

- 화면: 공통, 관리자, 생산, 품질, 장비, 시뮬레이터 연동 영역
- 서버: 인증 및 인가, API, 비즈니스 로직, 배치 및 스케줄러, 데이터 계층
- 운영 및 보안: 테넌트 분리, 키 관리, 백업 및 복구, 감사 및 원시 로그, 모니터링 및 경보

## 2. 우선순위 레벨 정의

- **P1 (Must, 최우선, 설계 단계부터 필수)**  
  - 잘못 설계하면 나중에 고치기 매우 어렵거나 보안 사고 및 데이터 유출, 구조 전체 재작업으로 이어질 수 있는 항목
  - 시스템 전체의 뼈대 및 보안 기본선에 해당하는 규칙

- **P2 (Should, 중요, 1차 상용 버전 내 반영)**  
  - 보안, 운영, 확장성에 매우 중요하나 P1 기반 위에서 단계적으로 구현해도 되는 항목

- **P3 (Nice to have, 고도화 단계)**  
  - 필수는 아니나 운영 안정성, 편의성, 보안 고도화를 위한 항목

### 2.1 P0 런칭 게이트 표기(추가 보완)

본 문서의 우선순위는 P1, P2, P3로 유지하되, **런칭 시점에 반드시 통과해야 하는 항목**은 각 요구사항에 `P0 게이트`로 표기한다.  
`P0 게이트`는 실서비스 제공 가능 여부를 좌우하는 필수 통제 항목으로, 설계, 구현, 테스트, 운영 런북까지 한 세트로 완료한다.

## 3. 코딩 표준 및 품질 원칙 (재사용성 및 단순성 중심)

본 장은 요구사항 구현 과정에서 “장애와 유지보수 비용”을 폭증시키는 실패 포인트를 사전 차단하기 위한 공통 원칙이다.  
P1부터 P3까지 모든 기능 구현에 동일하게 적용한다.

### 3.1 단순성 우선 규칙

- 한 함수 및 클래스는 한 가지 목적만 수행한다. 조건 분기와 예외가 늘어나면 즉시 분해한다.
- 업무 흐름은 `입력 → 검증 → 처리 → 저장 → 응답`의 직선형 파이프라인으로 유지한다.
- 과도한 패턴과 추상화는 지양한다. 외부 의존 분리가 필요한 지점에만 인터페이스를 사용한다.
- 하드코딩 금지: 경로, 주소, 키, 임계치, 타임존은 설정으로 분리한다.
- 변경 가능성이 큰 영역은 기능 확장보다 “경계와 규약”만 먼저 고정하고, 구현은 단계적으로 진행한다.

### 3.2 재사용성 설계 정책

- **3회 반복 기준**: 동일 로직이 3회 이상 반복될 때 공통화 후보로 승격한다.
- 업무 정책(자주 바뀌는 규칙)은 도메인에 남기고, 메커니즘(로깅, 검증 프레임, 재시도, 변환, 캐시)만 공통화한다.
- 거대한 유틸 클래스는 금지한다. 작은 함수 및 작은 컴포넌트를 조합하는 방식으로 재사용한다.
- 테스트 가능성이 재사용성이다. 핵심 로직은 DB 및 외부 연동과 분리하여 단위 테스트가 가능해야 한다.

### 3.3 예외 처리 및 복원력

- 예외를 숨기지 않는다. 사용자 메시지, 운영 로그, 개발 디버그 정보를 분리하여 기록한다.
- 재시도는 멱등성 설계와 함께 적용한다. 멱등 키 및 중복 처리 방지 로직이 없으면 재시도는 데이터 중복을 유발한다.
- 타임아웃을 명시하고, 연쇄 장애 방지를 위해 서킷 브레이커 및 폴백 전략을 준비한다.
- 부분 실패를 기본 시나리오로 간주한다. 외부 시스템 장애 시에도 핵심 서비스는 최소 기능으로 유지한다.

### 3.4 성능 및 리소스 관리

- DB 접근 규칙: 페이징 기본 적용, N+1 쿼리 금지, 인덱스 기준의 조회 설계
- 대용량 데이터는 전체 로딩 금지. 스트리밍 및 배치 처리로 메모리 사용량을 제한한다.
- 커넥션, 파일 핸들, 스레드, 타이머 누수 방지를 위해 수명주기 관리를 표준화한다.
- 성능 기준선(베이스라인)을 측정하고 변경 시 회귀 테스트로 검증한다.

### 3.5 보안 코딩 및 데이터 보호

- 입력 검증을 표준화한다. SQL Injection, Command Injection, Path Traversal을 원천 차단한다.
- 민감정보의 로그 출력 금지. 개인정보, 토큰, 키, 암호화 원문은 마스킹 또는 해시 처리한다.
- 키 관리 및 로테이션을 고려한 설계: 키는 코드 및 설정 파일에 저장하지 않는다.
- DB 저장 데이터는 암호화 정책을 일관 적용한다. 테넌트 분리와 접근 통제는 기본값이다.

### 3.6 코드 리뷰 체크리스트(요약)

| 점검 항목 | 기준 | 기대 효과 |
|---|---|---|
| 단순성 | 함수 책임 단일화, 분기 최소화, 하드코딩 제거 | 읽기 및 변경 용이성 |
| 재사용성 | 3회 반복 시 공통화, 공통화 단위 최소화 | 유틸 비대화 방지 |
| 예외 처리 | 표준 에러코드 및 로깅, 재시도 시 멱등성 확보 | 장애 분석 및 데이터 무결성 |
| 보안 | 입력 검증, 민감정보 마스킹, 권한 체크 | 취약점 예방 |
| 성능 | 페이징, 인덱스, N+1 제거, 대용량 스트리밍 | 비용 및 응답성 |
| 운영성 | 원시 로그 보관, 감사 추적, Correlation ID | 원인 추적 |
| 테스트 | 핵심 도메인 단위 테스트, 통합 테스트 최소 1세트 | 회귀 방지 |

### 3.7 시스템 아키텍처 단순화 원칙

- 레이어는 최소 구성으로 단순화한다: Presentation, Application, Domain, Infrastructure
- 모듈 분리는 많을수록 좋은 것이 아니라 경계가 명확할수록 좋다. 도메인 단위로 경계를 고정하고 내부 구현은 단계적으로 확장한다.
- 서비스 및 마이크로서비스 분리는 규모와 조직이 준비되기 전에는 보류한다. 초기에는 모듈형 모놀리식 구조로 운영 복잡성을 최소화하고, 병목이 명확해질 때만 분리한다.
- 공통 기능은 플랫폼 레벨로 표준화한다: 인증 및 인가, 로깅, 예외 처리, 설정, 공통 응답 포맷
- 업무 정책은 각 도메인에 남기고, 메커니즘은 공통화한다: 검증 프레임, 변환, 재시도, 캐시, 관측 로그

### 3.8 코드 구조 및 네이밍 표준(권장)

- 동일 개념은 동일 용어로 고정한다. 역할 혼용을 금지한다: DTO, Entity, Command, Query, Service, Repository
- 폴더 및 프로젝트 구조는 아래 4단을 기본으로 한다. 복잡한 패턴 없이도 확장과 재사용이 가능하다.
  - Core 또는 Domain: 엔티티, 값 객체, 핵심 규칙, 도메인 서비스
  - Application: 유스케이스, 트랜잭션 경계, DTO, 핸들러
  - Infrastructure: DB 접근 구현, 외부 API 및 파일, 메시징, 캐시
  - Presentation: API 컨트롤러, 화면, 입력 검증 1차, 호출 연결
- 공통 유틸은 작게 쪼개어 조합 재사용한다. 거대한 유틸 클래스, 만능 Helper는 금지한다.

### 3.9 배포 및 릴리즈 단순화 규칙

- 설정 및 시크릿은 코드에서 제거하고 환경 변수와 시크릿 저장소로 관리한다.
- 기능 노출은 Feature Flag로 제어한다. 테넌트 단위로 점진 배포하고 문제 시 즉시 비활성화한다.
- 배포는 안전한 스위치 작업이 되도록 설계한다: 단계적 배포, 롤백 경로, 마이그레이션 버전 관리

## 5. P1 최우선 필수 요구사항

### 5.1 데이터 보안 및 암호화 및 기밀성

**P1-1. 민감 데이터 및 개인정보 암호화 (P0 게이트)**  
- DB에 저장되는 개인정보 및 민감 데이터(예: 이름, 연락처, 이메일, 주소, 계좌번호, IP, User-Agent, 장비 식별자 등)는 컬럼 수준 암호화를 적용한다.
- 암호화 알고리즘은 AES-256 수준을 기준으로 한다.
- 비밀번호는 복호화 가능한 암호화가 아니라 해시 알고리즘(bcrypt, argon2 등)으로 저장하며 평문 저장은 절대 금지한다.
- 로그, 백업, 덤프 등 2차 저장 매체에서도 평문으로 민감 정보가 노출되지 않도록 설계한다.

**P1-2. 시크릿 및 암호화 키 관리 (P0 게이트)**  
- 암호화 키, JWT 시크릿, DB 계정 비밀번호 등은 코드에 하드코딩하지 않고 환경 변수 또는 전용 시크릿 관리 도구를 사용한다.
- 운영 환경에서 시크릿 파일 및 키에 대한 접근 권한은 최소화한다.
- 키 교체(로테이션) 전략을 수립하고, 키 유출 및 교체 시 대응 절차를 마련한다.

**P1-3. 통신 구간 암호화 (P0 게이트)**  
- 브라우저와 웹 서버 간 통신은 HTTPS(TLS) 기반으로 구성한다.
- 웹 서버와 DB, 서버와 외부 연계 시스템 간 통신도 가능한 한 암호화 채널을 사용하도록 설계한다.
- 클라우드 환경에서는 WAF, Reverse Proxy, 방화벽 정책으로 불필요한 포트 및 경로를 차단한다.

### 5.2 멀티테넌트(기업별 분리) 및 인증 및 권한 구조

**P1-4. 기업별 데이터 분리 및 멀티테넌트 구조 (P0 게이트)**  
- 시스템은 여러 기업이 동시에 사용하는 멀티테넌트 구조를 기본으로 한다.
- 모든 도메인 데이터(수주, 재고, 작업, 품질, 설비, 로그 등)는 Company(기업 단위) 기준으로 분리 관리한다.
- 구현 방식은 다음 중 하나를 명확히 선택해 일관되게 적용한다.  
  - 기업별 DB 분리  
  - 기업별 스키마 분리  
  - 단일 DB 내 모든 테이블에 `companyId` 컬럼을 두고 쿼리 레벨에서 강제 필터링  
- 어떤 방식이든 한 기업 사용자가 다른 기업 데이터에 접근하지 못하도록 구조적으로 보장한다.

**P1-5. 관리자 전용 기업 선택 및 권한 기반 접근 제어 (P0 게이트)**  
- 시스템 및 서비스 관리자는 기업 선택 드롭다운 또는 필터를 통해 특정 기업의 데이터만 조회 및 관리할 수 있어야 한다.
- 일반 사용자는 자신이 속한 기업의 데이터만 조회 및 수정 가능해야 하며 다른 기업 데이터는 접근 불가하다.
- JWT 토큰에는 최소한 다음 정보가 포함되어야 한다.  
  - 사용자 ID  
  - 소속 기업 ID(`companyId`)  
  - 역할(Role: SYSTEM_ADMIN, COMPANY_ADMIN, USER 등)
- 모든 API 및 서비스 로직에서 `companyId`와 `role` 기반 인가를 수행한다.

**P1-6. 인증 및 인가 보안 정책 (P0 게이트)**  
- 비밀번호 정책을 명확히 정의한다(최소 길이, 문자 조합 규칙).
- 로그인 실패 횟수 제한 및 계정 잠금 정책을 정의한다.
- JWT 유효 기간과 갱신 전략(Access 및 Refresh Token 사용 여부)을 정의한다.
- 역할별 권한 범위를 구체화하고 화면 및 API에 일관되게 적용한다.

- DB 설계 원칙

### 6.2 로그 및 모니터링 및 감사

**P2-4. 외부 연계 원시 로그 보관 및 관리자 조회 기능 (P0 게이트)**  
- 장비 및 외부 시스템 및 외부 API에서 수집된 원시 데이터(raw data)를 일정 기간 보관한다.
- 원시 로그 필드 최소 요건  
  - 수집 시각  
  - 수집 대상(장비, 시스템, API 등)  
  - 기업 ID(companyId)  
  - 원시 메시지 또는 요청 및 응답 내용(필요 시 부분 마스킹)  
  - 처리 결과(성공 및 실패, 오류 코드 등)
- 보관 기간과 파기 정책을 명시하고 기간이 지난 로그는 자동 정리 또는 장기 보관 정책에 따라 관리한다.
- 관리자 화면에서 기업별, 기간별, 대상별, 결과별 조회 및 검색 및 필터링이 가능해야 한다.

**P2-5. 감사 로그 및 보안 이벤트 모니터링**  
- 로그인 성공 및 실패, 비밀번호 변경, 사용자 생성 및 삭제 및 권한 변경, 기업 정보 변경, 주요 설정 변경 등 주요 보안 이벤트는 감사 로그로 남긴다.
- 감사 로그는 기업별로 구분 저장하며 관리자가 조회 가능한 UI를 제공한다.
- 이상 징후(로그인 실패 다수, 비정상 IP 접근 등) 경고 및 알림 기능 추가를 고려한다.

**P2-5-1. 표준 로그 포맷 및 Correlation ID 적용**  
- 모든 요청 및 작업에는 Correlation ID를 부여하고, API부터 DB 및 외부 연계까지 동일 ID로 전파한다.
- 운영 로그는 표준 필드를 포함한다: timestamp, tenant_id, user_id, correlation_id, action, result, latency_ms, error_code
- 개인 정보와 시크릿은 로그에 남기지 않는다. 필요 시 마스킹 또는 해시로 처리한다.

**P2-5-2. 핵심 운영 메트릭 및 경보 기본선**  
- 최소 메트릭을 표준화한다: 요청 수, 평균 및 P95 지연, 에러율, DB 쿼리 시간, 외부 연계 실패율

## 7. P3 고도화 및 운영 최적화 요구사항

### 7.1 백업 및 복구 보안

**P3-1. 백업 데이터 암호화 및 접근 통제**  
- 기업별 백업 파일은 암호화 적용 및 접근 권한 최소화를 원칙으로 한다.
- 정기 복원 테스트로 무결성과 복구 가능성을 검증한다.

### 7.2 키 로테이션 및 보안 정책 문서화

**P3-2. 키 로테이션 및 운영 보안 정책 문서화**  
- 암호화 키, JWT 시크릿 등의 로테이션 절차를 문서화한다.
- 정기 점검 및 회전 주기를 설정하고 유출 의심 시 신속 회전 절차를 마련한다.
- 운영 및 보안 정책(접근 통제, 로그 보관 기간, 패스워드 정책 변경 등)을 문서로 관리한다.

### 7.3 보안 및 운영 가이드 체계화

**P3-3. 보안 및 운영 가이드 문서 체계화**  
- 보안 가이드, 운영 가이드, 장비 연동 가이드를 체계적으로 관리한다.
- 신규 기능 개발 또는 아키텍처 변경 시 문서를 갱신하고 코드와 문서 일치 여부를 정기 점검한다.

## 8. 개발 및 운영 체크리스트

### 8.1 설계 단계
- P0 게이트 항목의 수용 기준 및 KPI가 정의되었는가
- 테넌트 분리 전략과 키 관리 전략이 문서화되었는가
- 백업 및 복구 시나리오와 복구 리허설 절차가 정의되었는가
- 원시 로그 보관 범위와 파기 정책이 정의되었는가
- 표준 에러코드와 표준 응답 포맷이 정의되었는가
- Feature Flag 정책과 점진 배포 및 즉시 차단 절차가 정의되었는가
- API 및 DB 변경 호환 절차(추가, 전환, 제거)가 정의되었는가

### 8.2 개발 단계
- 3장 코딩 표준의 단순성과 재사용성 규칙을 준수했는가
- 예외 처리 및 로깅 및 멱등성 설계가 포함되었는가
- Correlation ID 전파와 표준 로그 필드가 적용되었는가
- 호환 가능한 마이그레이션(무중단) 설계가 포함되었는가
- Feature Flag로 신규 기능이 안전하게 통제되는가
- 핵심 도메인 단위 테스트가 포함되었는가
- 성능 기준선 측정과 회귀 테스트 계획이 수립되었는가

### 8.3 배포 및 운영 단계
- 배포 후 모니터링 대시보드와 경보 규칙이 활성화되었는가
- 백업이 정상 수행되고 복구 리허설을 통과했는가
- 감사 로그와 원시 로그 조회가 운영자 동선에 맞게 제공되는가
- 장애 발생 시 운영 런북에 따라 조치 가능한가

## 9. 부록

### 9.1 표준 로그 필드 예시

운영 로그는 아래 필드를 포함하도록 표준화한다.

| 필드 | 설명 | 예시 | 필수 |
|---|---|---|:---:|
| timestamp | 발생 시각(Asia/Seoul) | 2025-12-13 17:05:11 | Y |
| tenant_id | 기업 식별자 | TENANT_0007 | Y |
| user_id | 사용자 식별자 | admin01 | Y |
| correlation_id | 요청 상관관계 ID | 9f2c...e10 | Y |
| action | 작업명 또는 API | ProdEvent.Create | Y |
| result | Success 또는 Failed | Success | Y |
| latency_ms | 처리 지연(ms) | 132 | Y |
| error_code | 표준 에러 코드 | MES-DB-409 | N |

### 9.2 표준 에러 코드 체계 예시

- 형식: `[도메인]-[컴포넌트]-[상태코드]`
- 예시: `MES-AUTH-401`, `MES-DB-409`, `MES-DEVICE-504`
- 사용자 메시지와 운영 메시지를 분리하여 제공한다.

---

### 9.3 권장 레이어 및 폴더 구조 예시

아래 구조는 복잡한 프레임워크를 추가하지 않고도 재사용성과 단순성을 동시에 확보하기 위한 최소 표준안이다.

```text
src/
  Core/                # Domain: 엔티티, 값 객체, 핵심 규칙
  Application/         # 유스케이스, 트랜잭션 경계, DTO
  Infrastructure/      # DB 및 외부 연동 구현, 캐시, 파일
  Presentation/        # API, UI, 화면, 입력 검증 1차
```

### 9.4 호환 가능한 변경 프로세스 예시

- 1단계 추가: 신규 필드 및 신규 엔드포인트는 추가만 하고 기존 동작은 유지한다.
- 2단계 전환: Feature Flag 또는 설정으로 새 경로를 선택적으로 활성화한다. 필요 시 이중 쓰기 및 검증을 수행한다.
- 3단계 제거: 충분한 유예 기간 후 구 기능과 구 필드를 제거한다. 제거 전 감사 로그 및 운영 지표로 영향 범위를 확인한다.

## 10. 요약 및 적용 원칙

1. **P1 요구사항은 설계 및 개발 전 과정에서 항상 준수해야 하는 기본 통제 기준이다.**  
   - 데이터 암호화, 키 관리, 통신 암호화  
   - 멀티테넌트 구조, 인증 및 인가 정책  
   - 코드 및 DB 및 SQL 단순성, 엄격한 검증, 운영 환경 및 배포 구조, 웹 취약점 대응

2. **P2 요구사항은 1차 상용 버전까지 반드시 구현해야 하는 항목이다.**  
   - 문서 기반 UI 및 UX  
   - 원시 로그 및 감사 로그  
   - 오픈소스 선정 및 취약점 관리  
   - 정기 백업 및 복구 리허설

3. **P3 요구사항은 운영 단계에서 보안 및 안정성을 고도화하기 위한 항목이다.**  
   - 백업 암호화 및 접근 통제  
   - 키 로테이션  
   - 보안 및 운영 문서 체계화

본 문서는 MES-System_v0.5 개발 전 과정에서 아키텍처 설계, DB 설계, API 설계, 화면 설계, 코드 구현, 테스트, 배포 및 운영까지 모든 단계의 체크리스트로 활용한다.
