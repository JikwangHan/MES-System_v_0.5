
# MES-System_v_0.5 요구사항 (우선순위 정리본)

## 1. 문서 개요

이 문서는 MES-System_v_0.5 프로젝트의 **전체 요구사항을 우선순위(P1, P2, P3)** 기준으로 정리한 문서이다.  
우선순위는 다음 기준을 종합적으로 고려하여 결정하였다.

- 신속성: 실제 개발 적용의 시급성
- 중요성: 시스템 목적 달성에 미치는 영향
- 보안성: 보안 사고 및 데이터 유출 방지와의 직접적 연관성
- 기밀성: 개인정보 및 민감 데이터 보호와의 연관성
- 시스템 관리 용이성: 운영, 유지보수, 배포, 장애 대응의 편의성
- 기능 확대 용이성: 향후 기능 추가/확장 시 구조적 유연성

---

## 2. 우선순위 레벨 정의

- **P1 (Must, 최우선·설계 단계부터 필수)**  
  - 잘못 설계하면 나중에 고치기 매우 어렵거나,  
    보안 사고/데이터 유출/구조 전체 재작업으로 이어질 수 있는 항목
  - 시스템 전체의 “뼈대”와 “보안 기본선”에 해당하는 규칙

- **P2 (Should, 중요·1차 상용 버전 내 반영)**  
  - 보안/운영/확장성에 매우 중요하지만,  
    P1 기반 위에서 단계적으로 구현해도 되는 항목

- **P3 (Nice to have, 고도화 단계)**  
  - 필수는 아니지만,  
  운영 안정성·편의성·보안 고도화를 위한 항목

## 3. P1 – 최우선 필수 요구사항

### 3.1 데이터 보안·암호화·기밀성

**P1-1. 민감 데이터 및 개인정보 암호화**

- DB에 저장되는 **개인정보 및 민감 데이터**(예: 이름, 연락처, 이메일, 주소, 계좌번호, IP, User-Agent, 장비 식별자 등)는 컬럼 수준 암호화를 적용한다.  
- 암호화 알고리즘은 **AES-256** 수준의 강력한 알고리즘을 기준으로 한다.  
- 비밀번호는 복호화 가능한 암호화가 아니라 **해시 알고리즘(bcrypt, argon2 등)**을 사용해 저장하며, 평문 저장은 절대 금지한다.  
- 로그, 백업, 덤프 등 2차 저장 매체에서도 평문으로 민감 정보가 노출되지 않도록 설계한다.

**P1-2. 시크릿 및 암호화 키 관리**

- 암호화 키, JWT 시크릿, DB 계정 비밀번호 등은 코드에 **하드코딩하지 않고**, 반드시 환경 변수(.env) 또는 전용 시크릿 관리 도구를 사용한다.  
- 운영 환경에서 시크릿 파일 및 키에 대한 접근 권한은 최소한으로 제한한다.  
- 장기적으로 키 교체(회전) 전략을 수립하고, 키 유출·교체 시 대응 절차를 마련한다.

**P1-3. 통신 구간 암호화**

- 브라우저(클라이언트)와 웹 서버 간 통신은 반드시 **HTTPS(TLS)** 기반으로 구성한다.  
- 웹 서버와 DB, 서버와 외부 연계 시스템 간 통신도 가능한 한 암호화 채널을 사용하도록 설계한다.  
- 클라우드 환경에서는 WAF, Reverse Proxy, 방화벽 설정 등을 활용해 불필요한 포트 및 경로를 차단한다.

### 3.2 멀티테넌트(기업별 분리) + 인증/권한 구조

**P1-4. 기업별 데이터 분리 및 멀티테넌트 구조**

- 시스템은 여러 기업(고객사)이 동시에 사용하는 **멀티테넌트 구조**를 기본으로 한다.  
- 모든 도메인 데이터(수주, 재고, 작업, 품질, 설비, 로그 등)는 **Company(기업 단위)** 기준으로 분리 관리한다.  
- 구현 방식은 다음 중 하나를 명확히 선택해 일관되게 적용한다.
  - 기업별 DB 분리
  - 기업별 스키마 분리
  - 단일 DB 내 모든 테이블에 `companyId` 컬럼을 두고, 쿼리 레벨에서 강제 필터링
- 어떤 방식이든 “한 기업 사용자가 다른 기업 데이터에 접근하지 못하도록” 구조적으로 보장해야 한다.

**P1-5. 관리자 전용 기업 선택 및 권한 기반 접근 제어**

- 시스템/서비스 관리자는 **기업 선택 드롭다운/필터**를 통해, 특정 기업을 선택하고 해당 기업의 데이터만 조회·관리할 수 있어야 한다.  
- 일반 사용자는 자신이 속한 기업의 데이터만 조회·수정 가능해야 하며, 다른 기업 데이터는 접근 불가하다.  
- JWT 토큰에는 최소한 다음 정보가 포함되어야 한다.
  - 사용자 ID
  - 소속 기업 ID(`companyId`)
  - 역할(Role: SYSTEM_ADMIN, COMPANY_ADMIN, USER 등)
- 모든 API 및 서비스 로직에서 `companyId`와 `role`을 기준으로 인가(Authorization)를 수행한다.

**P1-6. 인증 및 인가 보안 정책**

- 비밀번호 정책을 명확히 정의하고 적용한다.
  - 최소 길이, 문자 조합(대문자/소문자/숫자/특수문자 등)을 포함하는 규칙  
- 로그인 실패 횟수 제한 및 계정 잠금 정책을 정의한다.
  - 예: 연속 N회 로그인 실패 시 계정 잠금, 관리자 또는 본인 인증을 통한 해제 등  
- JWT 유효 기간과 갱신 전략(Access/Refresh Token 사용 여부)을 명확히 정의한다.  
- SYSTEM_ADMIN, COMPANY_ADMIN, 일반 USER 등 역할별 권한 범위를 구체적으로 정의하고, 화면·API에 일관되게 적용한다.

### 3.3 개발 방식·코드 품질

**P1-7. 코드, DBMS 구조, SQL의 단순성 및 메모리 사용 최소화**

- 모든 **소스코드, DBMS 구조(테이블/인덱스/관계 설계), SQL 문**은 가능한 복잡성을 배제하고 **단순한 구조**를 지향한다.
  - 과도한 추상화, 이해하기 어려운 패턴 남용, 과도하게 복잡한 쿼리(중첩 서브쿼리 난립 등)를 지양한다.
- DB 설계 시에도 다음 원칙을 따른다.
  - 필요한 컬럼과 테이블만 정의하고, 불필요한 중복/관계를 최소화한다.
  - 인덱스는 조회/조인 패턴을 고려해 최소 개수로 효과적으로 설계한다.
- SQL 작성 시에는 다음을 고려한다.
  - 단순하고 읽기 쉬운 쿼리부터 우선 적용하고, 성능 문제가 있을 때에만 단계적으로 최적화한다.
  - 조회량이 많은 화면은 페이지네이션, 서버 사이드 필터링/정렬을 적용한다.
- 전체 시스템의 메모리 사용량을 최소화하기 위해
  - 한번에 지나치게 많은 데이터(대용량 리스트 전체)를 가져오지 않고,
  - 필요 데이터만 선택적으로 조회/가공하는 방식을 우선 적용한다.

**P1-8. 엄격한 자체 검증과 에러·경고 최소화**

- 개발 과정에서 기능 동작 확인뿐 아니라, 예외 상황·엣지 케이스까지 고려한 자체 테스트를 수행한다.  
- TypeScript, ESLint, NestJS/React 경고 및 오류를 가능한 한 제거하고, 빌드 및 런타임 로그를 깨끗하게 유지한다.  
- 잠재적 오류 가능성이 있는 부분은 사전에 주석 및 문서로 명시하고, 우회·보완 방법을 함께 검토한다.

**P1-9. 주석 및 설명 – 초보자 기준 한글 상세**

- 중요한 로직·함수·클래스에는 **한글 주석**을 충분히 작성한다.  
- 주석은 초보자(일반인)도 이해할 수 있도록 다음을 포함한다.
  - 이 코드가 무엇을 하는지
  - 왜 이런 방식으로 구현했는지
- 모든 설명은 한글로, 개념과 배경을 포함해 자세히 작성한다.

### 3.4 아키텍처/운영 환경 + 단일 exe 배포

**P1-10. 로컬/클라우드 + Windows/Linux 운영 지원**

- 시스템은 로컬 서버와 클라우드 환경에서 모두 운영 가능해야 한다.  
- 운영 OS는 Windows 계열과 Linux 계열을 모두 지원하도록 설계한다.  
- 파일 경로, 프로세스 실행, 서비스 등록 등 OS 종속적인 요소는 최소화하거나, OS별 분기 처리를 명확히 한다.

**P1-11. 단일 exe 배포 및 DB 포함 설치**

- 최종 배포 형태는 **단일 exe 설치 파일** 1개로 한다.  
- exe 실행 시 다음 요소가 자동 설치·구축되도록 설계한다.
  - 웹 서버 런타임
  - 프론트엔드 정적 파일
  - DB(MariaDB 등)
  - 필수 라이브러리 및 설정 파일
- 초기 관리자 계정(admin/admin123) 및 기본 설정은 설치 과정에서 자동 또는 반자동으로 구성되도록 한다.

**P1-12. 운영 환경 최소 권한 원칙**

- 애플리케이션 서버와 DB 서버는 루트 계정이 아닌 **전용 서비스 계정**으로 실행한다.  
- 운영 서버에서 개방되는 포트는 서비스에 필요한 최소한만 허용하고, 나머지는 방화벽으로 차단한다.  
- 서버 및 DB 접근 권한은 최소 권한 원칙에 따라 구성하고, 계정·권한 사용 이력을 관리한다.

### 3.5 웹 취약점 대응 기본 원칙

**P1-13. OWASP Top 10 대응 원칙**

- SQL 인젝션 방지
  - ORM(TypeORM 등) 사용
  - 파라미터 바인딩 사용, 문자열 결합 쿼리 최소화

## 4. P2 – 중요(1차 상용 버전 내 반영) 요구사항

### 4.1 UI/UX 및 도메인 구조

**P2-1. UI/UX 기준 – 2025년 MES 웹서버 사용설명서 준수**

- `docs/2025년 MES 웹서버 사용설명서.pdf`에 포함된 화면 구조와 이미지를 기준으로 UI/UX를 설계·구현한다.  
- 주요 화면:
  - 메인 페이지(배경, 로고, 메뉴, 회사명/링크 등)
  - 로그인/회원가입 팝업
  - 대시보드
  - 수주 관리
  - 재고 관리
  - 작업/작업지시
  - 품질 관리
  - 설비/모니터링
  - 시스템/관리자 메뉴
- 버튼 위치, 그리드와 검색 영역 배치, 팝업 동작 등은 가능하면 문서와 동일하게 구현한다.

**P2-2. MES_Simulator 및 Smart-Factory_Monitoring 연동 고려**

- 기존 **MES_Simulator(Smart-Factory_Simulator)** 및 **Smart-Factory_Monitoring**에서 사용 중인
  - 통신 방식(TCP, 시리얼, Modbus, OPC-UA 등)
  - 데이터 포맷(JSON, CSV, 이진 프로토콜 등)
  을 참고해, 확장 가능한 연동 구조를 설계한다.
- 초기 버전에서는 필수 연동 대상 위주로 구현하고, 향후 점진적으로 대상 장비 및 기능을 확대한다.

**P2-3. 기능 변경·확장 용이성**

- 도메인별 모듈화 구조를 유지한다.
  - 예: 수주 모듈, 재고 모듈, 작업 모듈, 품질 모듈, 설비 모듈, 시스템관리 모듈 등
- 공통 UI 컴포넌트(그리드, 검색 패널, 모달, 버튼 그룹, 상태 뱃지 등)를 정의하고 재사용한다.
- 환경 설정(.env 등)을 통해 서버 URL, DB 접속, 외부 연동 주소 등을 손쉽게 변경 가능하도록 한다.

### 4.2 로그·모니터링·감사

**P2-4. 외부 연계 원시 로그 보관 및 관리자 조회 기능**

- 장비, 외부 시스템, 외부 API 등에서 수집된 **원시 데이터(raw data)**를 일정 기간 보관한다.  
- 원시 로그에는 최소한 다음 정보가 포함되어야 한다.
  - 수집 시각
  - 수집 대상(장비, 시스템, API 등)
  - 기업 ID(companyId)
  - 원시 메시지 또는 요청/응답 내용(필요 시 부분 마스킹)
  - 처리 결과(성공/실패, 오류 코드 등)
- **보관 기간**(예: 30일/90일)과 파기 정책을 명시하고, 기간이 지난 로그는 자동 정리 또는 장기 보관 정책에 따라 관리한다.
- 관리자 화면에서 이 로그를 기업별·기간별·대상별·결과별로 조회·검색·필터링 할 수 있어야 한다.

**P2-5. 감사 로그 및 보안 이벤트 모니터링**

- 다음과 같은 주요 보안 이벤트에 대해 감사 로그를 남긴다.
  - 로그인 성공/실패
  - 비밀번호 변경
  - 사용자 생성/삭제/권한 변경
  - 기업 정보 생성/수정/비활성화
  - 주요 설정 변경
- 감사 로그는 기업별로 구분 저장되며, 시스템/서비스 관리자가 조회 가능한 UI를 갖춘다.
- 향후 이상 징후(로그인 실패 다수, 비정상 IP 접근 등)에 대한 경고/알림 기능 추가를 고려한다.

### 4.3 오픈소스 및 라이브러리 관리

**P2-6. 오픈소스 선정 기준 준수**

- DBMS, Grid, Chart, UI, 차트 등은
  - 많이 사용되고,
  - 사용이 간단하며,
  - 디자인이 우수한 무료 오픈소스를 우선적으로 선택한다.
- 예시:
  - DB: MariaDB
  - 프론트엔드 UI: React + Ant Design
  - 차트: Recharts
- 라이선스(MIT, Apache-2.0 등)를 확인해 상용 서비스에도 문제 없는 라이브러리만 사용한다.
- 최종 exe 패키징 시 필요한 라이브러리가 자동 포함될 수 있도록 구조를 설계한다.

**P2-7. 라이브러리 취약점 및 업데이트 관리**

- npm audit, GitHub Dependabot 등의 도구를 활용하여 사용 중인 라이브러리의 보안 취약점을 정기적으로 점검한다.  
- 취약점이 발견된 경우:
  - 영향 범위를 분석하고,
  - 테스트 환경에서 버전 업그레이드를 검증한 뒤,
  - 운영 환경에 반영하는 절차를 따른다.

### 4.4 정기 백업 정책 및 자동 스케줄링

**P2-8. 정기 DB 백업 정책 및 자동 스케줄링**

- DB 장애, 하드웨어 고장, 랜섬웨어 감염, 운영 상 실수 등으로 인한  
  **데이터 유실 위험**을 최소화하기 위해, **정기 DB 백업 정책과 자동 스케줄링**을 반드시 도입한다.
- 백업/복구 목표(RPO/RTO)를 명시적으로 정의한다. 예: **RPO=1시간, RTO=4시간** 수준을 목표로 설계한다.
- 백업 주기
  - 1일 1회 이상 **전체 백업(Full Backup)**을 수행한다.  
  - 필요 시 1시간 또는 4시간 간격의 **증분/차등 백업**을 병행하여,  
    허용 가능한 데이터 손실 시간(RPO)에 맞춘다.
- 백업 대상 및 범위
  - 기업별 DB 또는 스키마 단위로 백업을 수행하여,  
    **기업별로 독립적인 복원**이 가능하도록 한다.
  - 시스템 공통 설정, 계정/권한 정보 등 **핵심 시스템 테이블**도 백업 대상에 포함한다.
- 백업 저장 위치 및 보관 기간
  - 백업 파일은 서버 내부 디스크뿐 아니라,  
    **외부 스토리지(NAS, 클라우드 스토리지 등)**에도 저장하는 것을 기본으로 고려한다.
  - 최소 보관 기간(예: 최근 30일/90일)을 정책으로 정하고,  
    기간이 지난 백업은 자동 정리하거나 장기 보관 정책에 따라 별도 관리한다.
- 백업 파일은 기본적으로 **암호화 저장**을 원칙으로 하여, 백업 매체 유출 시에도 평문 데이터가 노출되지 않도록 한다.
- 백업 자동화 및 모니터링
  - OS 스케줄러(cron, Windows Task Scheduler) 또는 백업 전용 서비스/도구를 사용해  
    **자동으로 백업**이 수행되도록 구성한다.
  - 백업 실패·성공 정보는 로그로 남기고,  
    관리자 화면 또는 알림(이메일, 대시보드 경고 등)으로 확인 가능해야 한다.
- 복원 테스트
  - 정기적으로 백업본을 별도 환경 또는 테스트 DB에 복원해보는  
    **복원 테스트 절차**를 운영한다.
  - 복원 테스트를 통해 백업 파일 손상, 권한 오류, 암호화 키 문제 등  
    실제 장애 시 복구를 막는 요인이 없는지 사전에 점검한다.


## 5. P3 – 고도화 및 운영 최적화 요구사항

### 5.1 백업 및 복구 보안

**P3-1. 백업 데이터 암호화 및 접근 통제**

- 기업별 백업 파일에는 데이터 암호화를 적용하여, 백업 파일이 유출되더라도 평문 데이터가 노출되지 않도록 한다.  
- 백업 파일이 저장되는 스토리지(로컬, NAS, 클라우드 스토리지 등)에 대한 접근 권한을 제한하고, 접근 가능한 계정·사용자를 최소화한다.  
- 정기적으로 복원 테스트를 수행하여, 백업 데이터의 무결성과 복구 가능성을 검증한다.

### 5.2 키 회전 및 보안 정책 문서화

**P3-2. 키 회전 및 운영 보안 정책 문서화**

- 암호화 키, JWT 시크릿 등의 교체(회전) 절차를 문서화한다.
- 정기 점검 및 회전 주기를 설정하고, 키 유출 의심 시 신속히 회전할 수 있는 절차를 마련한다.
- 운영·보안 정책(접근 통제, 로그 보관 기간, 패스워드 정책 변경 등)을 문서로 관리한다.

### 5.3 보안/운영 가이드 체계화

**P3-3. 보안 및 운영 가이드 문서 체계화**

- React2Shell 대응 가이드 등 이미 작성된 보안 가이드 문서를 포함하여, 다음 문서들을 체계적으로 관리한다.
  - 보안 가이드(Security Guideline)
  - 운영 가이드(Operation Guideline)
  - 장비 연동 가이드(Device Integration Guideline)
- 신규 기능 개발 또는 아키텍처 변경 시 관련 문서를 갱신하고, 실제 코드와 문서가 일치하는지 정기적으로 점검한다.
